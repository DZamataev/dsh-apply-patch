# dsh-apply-patch

A Codex-style `apply_patch` tool for [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) (DSH), meant for GPT models that were trained on OpenAI's Codex patch format. It is mounted inside an Agent Preset, so only the Agents of that preset get it.

Fork of [drscrewdriver/dsh-patch-edit-plus](https://github.com/drscrewdriver/dsh-patch-edit-plus) 0.4.3, largely rewritten; see [NOTICE.md](NOTICE.md) and [CHANGELOG.md](CHANGELOG.md).

## What the model sees

One tool, `apply_patch`, with `input` (the whole patch) and an optional `dry_run`. The description teaches the Codex format:

```
*** Begin Patch
*** Update File: path/to/file.py
@@ def greet():
-    print("Hi")
+    print("Hello")
*** Add File: path/to/new.py
+print("new file")
*** Delete File: path/to/old.py
*** End Patch
```

`*** Move to:` renames, stacked `@@ line` labels narrow the place, `*** End of File` pins a change to the end (unless all its unchanged and removed lines are blank, see Codex patches). A git or unified diff is accepted too. The result text lists the files (`A`/`M`/`D`) with their paths as the model wrote them; the display diffs (see Display diffs) are not part of the text.

## Behaviour

- **Checked before written.** Every file is resolved, read and patched in memory first, and nothing is written unless all of it succeeds. A dry run performs the same checks: parsing, matching, read-before-write, and sandbox containment of every path the patch would write, move or remove. It cannot predict failures that only the operating system reports when the files are changed, such as a parent directory without write permission, a full disk or an I/O error; a real run that hits one fails and undoes its earlier steps.
- **Read before write.** With DSH's `fs-observation-policy`, a file must have been read with the `read` tool (or `read_image`), and must not have changed since, before the patch may update, move or delete it. The patch's own writes count as reads, so the same file can be patched again.
- **Guarded steps.** Updates and added files are written first, then moves, then deletions. Every step is guarded by the version the patch expects: the version checked while preparing for existing files, the version our own step left for created and moved files. A file that changed in between is not overwritten, moved or removed; the patch fails with `PATCH_STALE`.
- **Undo on failure.** When a step fails, the earlier steps are undone in reverse order with the same guards, also after the call was aborted. A moved file is moved back and a deleted file is put back as the very same file (inode, bytes, permission bits); an updated file gets its text back. A file someone else changed or created meanwhile is left as it is, and our copy is kept and named (a moved file stays at its destination, a deleted one in its staging directory). The error names every such file and any file whose state is unknown; it says "No file had been changed" only when that is known.
- **Observations.** After a successful patch every changed file counts as read at its new version. After a failed one only the files the undo put back do; anything else must be read again.
- **Same bytes as the reference.** A Codex patch leaves the bytes codex-rs `apply-patch` would; a unified diff leaves the bytes plain `git apply` (without `--unidiff-zero`) would. Where that is not possible the patch fails with `PATCH_PARSE` or `PATCH_CONFLICT` instead of writing a different file. The accepted extras below are cases the reference rejects; the only cases the reference accepts and this tool refuses are context-free unified hunks away from the end of the file, hunks git would apply by joining lines, unified diffs that change or set a file mode, unified diffs whose old mode names a symbolic link, directory or submodule entry (git patches such an entry when the path is one), negative modes, which git wraps around to another mode, `/dev/null` names that git reads as a file `dev/null`, a bare `---`/`+++` pair whose only hunk adds lines to a file that does not exist (git then creates it), sections that git reads with a `-p0` it guessed from an earlier bare pair, `@@ @@` hunks without line numbers next to anything git applies, which git skips as text, file names that are not valid UTF-8 anywhere in the name, also in a first component git removes (`"a\377/f"`, which git reads as `f`), whose bytes git writes where the file system takes them, C-quoted names holding a NUL byte anywhere in the name (`"a/f\000x"`, which git cuts at it and reads as `f`; `--- "a\000z/f"` with `+++ "b\000z/f"`, from which git keeps `a` and `b`, guesses `-p0` and patches `b`), and a patch that names one file in more than one section, such as a repeated new-file or rename section, which git applies section by section to the original file, so the last new file written wins and two renames of `f` leave two copies (`PATCH_CONFLICT` "change each file once per patch"; see Unified diffs).
- **Codex patches.** Markers, `@@` labels and paths are trimmed as Rust trims them (Unicode White_Space: U+0085 counts, a BOM does not); an operation's path is the rest of its header line without trailing whitespace, so `*** Add File:  x` names ` x`, as in codex-rs. A change is found with an exact match first, then tolerating trailing whitespace, surrounding whitespace (Unicode White_Space as Rust trims it: U+0085 counts, a BOM does not) and typographic punctuation, as in codex-rs; a tolerant match that fits more than one place is refused (codex-rs takes the first; the error lists up to five places). Context lines keep the file's own text, so only `-`/`+` lines change. Untouched lines keep their own line ending (LF, CRLF or lone CR); new lines take the file's first line ending; the updated file always ends with a line ending. A change with only `+` lines is appended at the end of the file, also after an `@@` label. `@@ label` is the text after `@@ ` without trailing whitespace; `*** End of File` and `@@` count as markers only unindented. An unprefixed blank line is blank context; a change that matches nowhere is retried without its last blank line, as in codex-rs (a change left with no old lines is then inserted where the search stands, also with `*** End of File`). Extras: stacked `@@` labels, a first change without `@@`, an update with only `*** Move to:` (the file is moved byte for byte), several unprefixed blank lines at the end of a change, all dropped when the change matches nowhere with them (codex-rs drops only the last), text around `*** Begin Patch`/`*** End Patch`, a first line written without the file's byte order mark (see Files).
- **Unified diffs.** Lines match exactly, line endings and whitespace included: a CR in the diff belongs to its line, as for git (a hunk line holding only a CR is a `PATCH_PARSE` error, git: "corrupt patch"; an empty context line of a CRLF file is a space and the CR), and `\ No newline at end of file` removes the LF of the line it follows, which must agree with the file. A marker is a line starting with `\ ` as git reads one (in any language; inside a hunk at least 12 bytes with its LF); any other line starting with `\` inside a hunk is a `PATCH_PARSE` error. git compares a marked line as a byte prefix, so it may match it against a line that has a newline and join the next line onto the new text; such a hunk is refused with `PATCH_CONFLICT`, and applied only where its marked line is the file's real last line without a newline. Hunk bodies are read by their header counts, so a body line such as `--- x` stays a change line; file headers count only between hunks. Hunks are placed as git places them, one after another and not necessarily in file order: a hunk whose header starts at line 0 or 1 must start at the beginning of the file, one without context lines after its last change must end at the end of the file (both, if both apply), otherwise the exact match nearest to the header's new line wins, the later one on a tie; lines an earlier hunk wrote are not matched again. When the anchoring fails the hunk is refused, never placed elsewhere. A hunk without any context lines (`git diff -U0`) applies only where its header points; plain `git apply` would move it to the end of the file, so it is refused with advice to add context or use the Codex format. Git header lines (`index`, `old mode`/`new mode`, `new file mode`, `deleted file mode`, `rename from`/`rename to`, `similarity index`, `---`/`+++`) count only right after a `diff --git` line, up to the first line that is not one, as `git apply` reads them; after a hunk or before a bare `---`/`+++` pair they are text and skipped, as git skips them. In that header a `---`/`+++` name must agree with earlier lines (`rename to g` then `+++ b/f` is a `PATCH_PARSE` error), `/dev/null` needs the `new file mode`/`deleted file mode` line (git would otherwise patch a file named `dev/null`), a rename needs both `rename from` and `rename to`, a mode must be octal, and only one of new file, deleted file and rename may be given. A file whose old and new names differ there (rename lines, or differing `---`/`+++` names) is moved, as with git. A `diff --git` line without header lines is text, as for git, and so is a bare `---`/`+++` pair without hunks, also with `/dev/null` on one side: only a `diff --git` section with `new file mode` or `deleted file mode` creates or deletes a file without hunks, and a diff of only such pairs is a `PATCH_PARSE` error (git: "No valid patches in input"); a section whose header lines are not followed by a hunk must be a new file, a deletion, a rename or a mode change, otherwise it is a `PATCH_PARSE` error, as is any text, a blank line included, between a `+++` header and the first hunk. Modes are read as git reads them (`strtoul`: a `+` sign and leading zeros are accepted, an overlong value keeps its low 32 bits) and compared as git canonicalizes them (`100664` is `100644`, `100775` is `100755`). A header that would change or set a mode is refused as a whole patch with `PATCH_UNSUPPORTED` before anything is written, also in a dry run, because git would change the mode and this tool writes file contents only: a `new mode` line that differs from the old mode or comes without one (with or without hunks, also next to a rename), and a `new file mode` other than `100644` (an executable file, a symbolic link, a submodule entry). `deleted file mode`, a lone `old mode` line and the mode of an `index` line only state the old mode and are accepted, as git accepts them, when that mode is a regular file (`100644` or `100755`); a symbolic link, directory or submodule mode there is refused with `PATCH_UNSUPPORTED` before anything is written (only regular files are patched; git rejects it for a regular file: "wrong type"). A negative mode on any of these lines is refused with `PATCH_UNSUPPORTED` too: git wraps it around to another mode (`new file mode -100644` creates a submodule directory, `new mode -100644` fails as a type change). `copy from`/`copy to` headers and binary patches are refused (`PATCH_PARSE`). A new file's hunks may have only `+` lines (git: "depends on old contents"); they are placed against an empty file as git places hunks, so a second hunk that again starts at line 0 or 1 is refused as git refuses it. A context-free hunk whose old lines span the whole current text (a new file's first hunk, a deletion of the whole file) has only one place and applies whatever line its header names, as with git. Header names are read as `git apply` reads them: `---`/`+++` names up to a TAB (git ends a path with a trailing space with one) or a CR, `rename from`/`rename to` names after the prefix up to a CR, a C-quoted name up to its closing quote; in a `diff --git` section a `---`/`+++` name loses its first path component (`-p1`; a name without `/` names nothing, as for git). A bare `---`/`+++` pair is read as git reads a traditional patch: each name loses its first path component, whatever it is (`--- x/f` names `f`, `--- /x/f` names `x/f`), unless both names lack a directory (or one is `/dev/null` and the `+++` name lacks one), from which git guesses `-p0` and reads the names whole; a timestamp at the end of a line (a date, optionally a time with a fraction and a zone, after a TAB or spaces) is not part of the name, so `--- a/my f 2010-07-05 19:41:17` names `my f`; of two differing names the `+++` one is patched, unless the `---` one is a shorter prefix of it (`--- a/f`, `+++ b/f.orig` patches `f`); an epoch timestamp after a TAB (`1970-01-01 00:00:00 +0000`, GNU diff's mark of an absent file) makes the pair create (on the `---` line) or delete (on the `+++` line) the file. A pair where git finds no name (`--- f` with `+++ /dev/null`, names that are empty after the first component) or has `/dev/null` on both sides is a `PATCH_PARSE` error. git keeps a guessed `-p0` for the rest of the patch, so it would read a later `diff --git a/f b/f` section or a later `--- a/f`/`+++ b/f` pair with `a/` and `b/` (moving `a/f` over `b/f`, or patching `b/f`); after such a guess a later `diff --git` line, and a later pair whose name has a directory, is a `PATCH_PARSE` error. An `@@ @@` hunk without line numbers is not a hunk for git, which skips it as text; it is applied only where git rejects the whole patch (every hunk unnumbered, no new file, deletion or rename section), placed at its first exact match after the previous hunk, and next to a numbered hunk or such a section, which git would apply without it, it is a `PATCH_PARSE` error asking for line numbers in every `@@` header or the Codex format. It names its file as git would name it with numbers and changes no guess for later sections. Every file name a unified diff gives to an operation (the old name of an update, a deletion or a rename, the new name of anything but a deletion) is checked as git checks it before writing (`read-cache.c` `verify_path`, with git's defaults `core.protectNTFS` on and `core.protectHFS` on macOS), and refused as a whole patch with `PATCH_PARSE` "invalid path" otherwise: no `.`, `..` or empty component (`--- a/./f`, `rename to ../g`), no leading `/` left after the first component is removed (`--- a//etc/f`), no trailing `/`, no `.git` component in any case (`.git/config`, `x/.GIT/y`), nor what NTFS reads as one (`.git.`, `.git `, `.git:x`, `git~1`, also after a backslash) or, on macOS, HFS+ (`.git` with zero-width or directional marks or U+FEFF); `.gitignore`, `.gitfoo`, `..foo` and `x.git` are names like any other. A C-quoted name is decoded from its bytes as UTF-8, a leading byte order mark included (`"\357\273\277g"` names U+FEFF followed by `g`, as for git); a name holding a NUL byte (`\000`) is refused with `PATCH_UNSUPPORTED` before anything is written, since git would cut the name at it, which can change the components it removes and the file it patches; a name that is not valid UTF-8 (`"a/\377"`), like a name holding a lone surrogate, is refused with `PATCH_UNSUPPORTED`, since files are named by UTF-8 text here. Both checks read every name as written (on the `diff --git` line when header lines follow it, `---`/`+++` names of a `diff --git` section or of a bare pair with hunks, `rename from`/`rename to` names), before a first component is removed, `-p0` is guessed, a timestamp is cut or names are compared, and refuse the whole patch; git's path rules above apply to the name that is left. A `diff --git` line names a file by itself only where both its names, after their first component, are the same bytes up to the line end, separated by one space or TAB (or are quoted, as git compares quoted names); a CR at the end of a CRLF `diff --git` line belongs to the second name, so such a line names no file, and a CRLF section named only by it (an empty `new file mode` or `deleted file mode` section, or one with only an `index` line) is a `PATCH_PARSE` error, as git rejects it ("lacks filename information"); CRLF `---`/`+++` and rename lines name the file as for git. A deletion's hunks must remove the whole file. An unprefixed line inside a hunk, or more `-`/`+` lines than the header declares, is a `PATCH_PARSE` error with the line number. Extras: a last line without its LF (git: "corrupt patch"), overstated counts at the end of the text or before the next hunk, `@@ @@` headers without numbers in a patch that has only such hunks, prose, fences and blank lines around the diff and between hunks (git accepts nothing between hunks), a first line written without the file's byte order mark (see Files).
- **Large files.** Applying a patch costs about the size of the file once plus the size of its changes and the places tried for them: the hunks of a unified diff replace lines in one line array; a numbered hunk is tried at the places nearest to its header one by one, as git tries them, and once that has cost about the size of the file, all its places are found in one pass over the file, so a hunk far from its header costs the file plus the hunk however repetitive the file is; an `@@ @@` hunk without line numbers is found in one such pass. The Codex changes of a file share one search: each tolerance level normalizes the file lines once and, from its second search on, indexes them by text, so a change costs about the places of its rarest line, not the rest of the file; a change whose lines are frequent in the file, as in rows of identical lines, is searched in one pass over the rest of the file instead (many near matches do not multiply it). 200 small hunks in a 4 MB file of 100,000 lines apply in about 10 ms, in both formats; a numbered hunk removing 6,000 identical lines whose header is 194,000 lines off in a 3.2 MB file applies in about 45 ms; 2,000 Codex changes found only without the trailing spaces of an 8 MB file of 200,000 lines apply in about 0.1 s; a Codex change of 1,000 identical context lines and one unique line at the end of 200,000 identical lines is found in about 30 ms, and a stale one of 3,000 such lines is refused in about 0.2 s; the same holds for an `@@ @@` hunk. Each unified hunk is spliced into the line array, which moves the lines after it, so many hunks in a very large file cost the file size times the hunks: 8,000 one-line insertions (a valid 449 KB diff) into a 13.3 MB file of 1.2 million lines take about 6.2 s through the tool (plain `git apply` takes 3.6 s on the same input; the bytes are the same).
- **Files.** Codex changes must be in file order. Parent directories of new files and move destinations are created. A move without changes keeps the file itself, byte for byte with its mode (setuid, setgid and sticky included). A UTF-8 byte order mark belongs to the first line when matching, as for codex-rs and git; when the reference would refuse a change because of it (a first line written without the mark, which the read tool does not show), the change is applied after the mark, for Codex patches and unified diffs alike; where the reference accepts the change, its bytes are kept. Either way the mark stays in the file, also after an undo.
- **Paths** are relative to the session's working directory; Codex paths may also be absolute, while unified diff names follow git's rules (see Unified diffs). Read-only mode refuses the whole patch up front. In `workspace-write` mode every path the patch writes (Add, a changed Update, a move destination), moves or removes, and every staging directory, must lie under the workspace root, `/tmp` or the platform temp directory, the roots the DSH fs sandbox allows writing; any other is refused with `PATCH_SANDBOX` while preparing, so before anything is written and also in a dry run.
- **Delete and move.** `ctx.fs` cannot rename or delete, so moves and deletions run one constant POSIX `sh` command through the session's shell, with the paths in environment variables and the call's sandbox policy. It relinks a file: `ln` gives it the new name (`ln` never replaces an existing name), and the old name is removed with `rm` only while `[ old -ef new ]` still says both name the same file; when that removal fails, the new name is removed again. The file keeps its inode, bytes and full mode. Move to relinks the source to the destination (creating missing parent directories with `mkdir -p`); with changes, the new text is then written through `ctx.fs` with the version the move left. The destination is taken as this patch's only after a stat, a read and a second stat agree that it holds the source's text. Delete File relinks the file into a private staging directory next to it (`.dsh-apply-patch-trash-<random>`, mode 700). A staging directory is used only when the relink's own `mkdir -m 700` created it; when the name exists already, another random name is tried (up to three), and a directory whose creation is unknown is never removed. The staged file must hold the bytes checked while preparing (SHA-256 over the whole file, binary included, read up to the size its first stat reported; a version change between read windows ends the check at once, and the call's abort signal ends it while applying, not while undoing); otherwise it is put back if its name is free, or kept and named, and the patch fails with `PATCH_STALE`. After the whole patch succeeded each staged file is checked again (version and bytes) and removed with `rm -f`, then its directory with `rmdir`, which removes only an empty directory; a staged file that changed is kept, and it and any directory that could not be removed are named in the result (`Note: …`). Undoing an added file stages it the same way, checked against the text written, and that staging is removed after the undo; an undone move or deletion counts as undone only when the file put back holds its text or bytes. Each relink stats the old name just before the command and runs only if it is still the expected version, then stats both names to learn the outcome, whatever the shell reported. In `workspace-write` mode every path the shell changes (the file, a move destination, a staging directory) must be inside the workspace or the temp directories, checked up front, also when the shell itself does not confine commands. Without a POSIX shell (none mounted, or Windows), patches with Delete File, Move to, or Add File together with other operations are refused with `PATCH_UNSUPPORTED` before anything is written; a patch that only updates files or adds one file works.
- **Symbolic links.** Update and Add write through a link to its target, like the native `write` tool. Delete File and Move to refuse a path that is itself a symbolic link (the link is never followed to remove its target); a file reached through a linked directory is handled normally. Add File refuses a path where a dangling link exists.
- **Display diffs.** The result value's `diffs`, copied into the tool result's `meta.diffs` (persisted with the Session log), hold one entry `{ path, oldText, newText }` per changed region of a file. The regions come from the edits the patch actually made (each Codex change or unified hunk where it was applied, and the line ending a Codex patch adds to a last line without one), not from comparing whole files: the characters an edit leaves equal at its start and end do not count, the lines it touches are changed lines, edits at most 6 unchanged lines apart share a hunk, and each hunk has up to 3 unchanged lines on each side, so hunks follow the edits rather than a shortest diff. A fragment (`oldText`, `newText`) is its lines, each followed by LF (`lines.join('\n') + '\n'`), the form of a whole file text as native `write` reports it: DSH's Web `DiffBlock` drops one final LF as the file's terminator, so it gets the exact lines back, and a blank line added or removed at the end of a hunk counts as a line (joined without that LF, `a\n` → `a\n\n` would show as equal sides). CRLF and LF are not shown, a lone CR stays in its line, and a leading byte order mark is not shown; lines are compared with their line endings, so a change of only a line ending is a hunk whose sides look equal. When a fragment ends with the file's last line and the file has no final line ending, the fragment ends without LF (`lines.join('\n')`), so `DiffBlock` again gets exactly the file's lines (`first\nlast` → `first\nLAST\n` shows `first`, `last` against `first`, `LAST`). Known limitation of this format: it has no marker for a missing final line ending (git's `\ No newline at end of file` would show as a content line), so a change that only adds or removes the final line ending shows as a hunk whose sides look equal; the entry is still emitted, so the file is listed. An added file has one entry with `oldText: null` and its whole text; a deleted file one entry with its old text and `newText: ''` (none for a binary or empty file); a modified or moved file one entry per hunk (none when its text is unchanged, as for a plain move); `oldText` is also `null` for a hunk of a file that was empty. `path` is the resolved absolute path in the file system's execution world (`ctx.fs.processPath`, the destination of a moved file), as native `write` and `edit` put it in their metadata, so an entry still names its file after the session changes directory and entries of one file share one path; the files list and the text keep the paths as written. An entry whose UTF-8 size (path and both texts) exceeds `maxDiffBytes` (16 KiB) keeps its path with empty texts and `truncated: true`, and the other hunks of the file stay; entries are kept in order until the next would bring the call over `maxDiffTotalBytes` (128 KiB), after which the rest of each file gets one truncated entry without its texts being computed, so a 50-file patch adds at most about 128 KiB plus a path per file. The work is proportional to the edits and the shown lines, not to the file sizes: a 365 KB Codex patch replacing one line every 2,400 lines in 50 files of 1.2 million lines gets its display diffs in about 3 ms. Patch application does not depend on any of this. The `presentResult` presenter turns the entries that are not truncated into a `diff` card.
- **Errors** are `PatchError` (a DSH `HarnessError`), so the tool result carries `{ name, code }`: `PATCH_PARSE`, `PATCH_CONFLICT`, `PATCH_NOT_OBSERVED`, `PATCH_STALE`, `PATCH_SANDBOX`, `PATCH_IO`, `PATCH_UNSUPPORTED`, `PATCH_LIMIT`.

## Use

Install it as a plain dependency of the DSH profile (not a bundle; the package deliberately has no `dsh.bundle`), then add a row to an Agent Preset:

```yaml
- id: apply-patch
  name: '@local/dsh-apply-patch'
```

Disable the native `edit`/`write` in that preset (`dsh-tool-fs` with `write: false, edit: false`) if the model should use only `apply_patch`. A second tool named `apply_patch` in the same scope makes the row fail to load.

| Option | Default | Meaning |
|---|---|---|
| `toolName` | `apply_patch` | Tool name |
| `allowCodexPatch` | `true` | Accept Codex patches |
| `allowUnifiedDiff` | `true` | Accept git/unified diffs |
| `maxFiles` | `50` | File operations per patch |
| `maxPatchBytes` | `524288` | Patch size in UTF-8 bytes |
| `maxDiffBytes` | `16384` | Size of one display diff entry (a hunk) in UTF-8 bytes |
| `maxDiffTotalBytes` | `131072` | Size of all display diff entries of one call in UTF-8 bytes |

## Develop

```sh
npm install --legacy-peer-deps
npm run check   # typecheck, tests (parsers, content, exact output bytes, and real fs-local or fs-sandbox + sandbox-policy / fs-observation-policy / bash-local), build; lib/ must be committed up to date
```

`lib/` is committed so the package installs from a git checkout without a build.

## Known limitations

- Codex changes within one file must be listed in file order.
- Unified hunks are spliced into the file's line array one by one, so the cost grows with the file size times the number of hunks (see Large files: 8,000 hunks in a 13.3 MB file take about 6.2 s, plain `git apply` 3.6 s).
- A unified hunk without context lines applies only at the end of the file, where its header must point; elsewhere it is refused (plain `git apply` would move it to the end of the file). Send `git diff` output with context, or a Codex patch.
- Deleting a binary file needs an observation of it, which only `read_image` gives for images; delete other binary files with the shell.
- A move or deletion checks the file version and then runs the shell command; the two are not atomic (see Threat model). Closing that window needs a versioned rename in `ctx.fs`.
- Moves and deletions need hard links on the file system and the right to link the file (Linux `fs.protected_hardlinks` refuses linking another user's file unless it is readable and writable); where `ln` fails, the patch fails before changing that file. A file with several hard links keeps its other links.
- Staging directories appear in the file's directory for the duration of the call (and stay when their removal fails, a staged file changed, or an undo had to keep a copy; the result or error names them). Deleting a large file reads it twice more to compute its digest.
- Writes rely on `ctx.fs.writeText` either publishing atomically or failing; a write that reports failure is taken as not done.
- No `sandbox_permissions` escalation parameter: a write the sandbox denies fails with the `[sandbox: …]` marker.
- Codex `@@` labels are matched as single lines; a label that occurs earlier than intended in the file must be made more specific.
- A unified diff written without the CRs of a CRLF file, or without `\ No newline at end of file` for a file lacking its final newline, does not apply (as with git); the error says so and suggests the Codex format, which keeps line endings.
- Updates are written through `ctx.fs.writeText`, which replaces the file and keeps only its `0777` permission bits: an updated file, a moved file with changes, and their undo lose setuid, setgid and sticky bits and get a new inode. A file created by Add File gets the default mode of `ctx.fs`. A change by someone else that leaves exactly the text this patch wrote cannot be told apart from it.
- Delete File and Move to are unavailable on Windows.
- File modes are never changed or set: a unified diff with a mode change, or a new file that is executable, a symbolic link or a submodule entry, is refused with `PATCH_UNSUPPORTED`, as is an old mode that is not a regular file and any negative mode. Change modes with the shell and send the content change without the mode lines.
- `ctx.fs` does not report file modes, so an old mode (`old mode`, `index`, `deleted file mode`) is not compared with the file's mode: where they differ between `100644` and `100755`, git warns and, with an equal `new mode` line, sets the file to that mode; this tool keeps the file's mode.
- Unified diff names are checked with git's default `core.protectNTFS` and `core.protectHFS` settings for the platform; a repository's own setting of them is not read. On Windows a drive prefix and backslashes are refused, but the other name rules git applies there (reserved names such as `CON`, trailing dots and spaces) are left to the file system.
- DSH's Web client (as of `deepseek-harness` `develop@bb159fa6d3`) draws inline diff cards only for the native `write`, `edit` and `str_replace_editor` calls and reads no `meta.diffs` of other tools; an `apply_patch` call shows as a generic row, grouped under "Edited files" by its name, and the turn's changed-files card comes from `dsh-workspace-changes`, which captures the files through the `fs/write-intent` waterfall this tool calls. No Host bridge in that version consumes `presentCall`/`presentResult` views; `presentCall` stays generic because a pure presenter cannot resolve paths.
- A header path with trailing spaces but no TAB after it (hand-written) keeps the spaces, as in git, and therefore usually names a file that does not exist.

## Threat model

The patch is protected against benign concurrent changes: an editor saving, a formatter, a watcher, another agent. Such a change is never overwritten, moved or removed, and a patch never reports success for a step that did not happen: every step checks the version it expects just before acting and stats the result afterwards. When a concurrent change makes a step or its undo impossible, the other party's file is left as it is, this patch's copy is kept under a named path, and the error says so.

A hostile process of the same user that swaps files, directories or symbolic links between a check and the single command that follows it is out of scope. `ctx.fs` has no atomic rename or delete, so short windows remain: a file swapped in between the version check and `ln` is moved or staged instead of ours (a staged one with other bytes is detected and put back or kept), a file put at the old name between `[ -ef ]` and `rm` (one system call) loses that name, and a staged file changed between its last check and `rm -f` (one command) is removed. An editor that writes the file in place while it is staged changes the staged file; its bytes then differ, so the file is put back or kept, never removed. A file being moved keeps such an edit at its destination, which is taken as this patch's only when it holds the source's text. An editor that saves by renaming a new file over the old name is seen by `[ -ef ]`, except within that single system call. A change that leaves exactly the bytes this patch expects cannot be told apart from them.
